# Native Task active delivery: first backend stage

This document records opt-in direct-parent delivery through Apexo's canonical Session inbox. Both tool-owned and fresh operator/HTTP completed-child continuation are now integrated, as detailed in the latest checkpoint below. Legitimate descendant routing, headless input attribution and source-specific sender quotas remain follow-on requirements. Operator controls are recorded separately in [native-task-message-ui.md](native-task-message-ui.md). Grok Build is reference evidence only; no feature invokes or embeds its runtime.

## Contract

The active-launch rules below retain their original meaning. The separate completed-child continuation path starts a new canonical owned Task launch in the same child Session; it does not reopen a closed launch or replay old provider work.

Set `task.activeMessages: true` in native or supported V1 configuration. The default is false, malformed explicit Task configuration fails closed, and a launch captures its capability. Current configuration and sender authority are checked again after permission evaluation. Immutable Task depth, parent/child Created proofs, live permissions, command sandbox and Goal attempt accounting remain authoritative. Admission and promotion transactions revalidate both receiver and sender captured Goal attempts; pause, replacement or budget exhaustion rejects new input even before the launch closes. Headless and managed Workflow/reviewer sends are refused.

`send_subagent_message` accepts a direct child's Session ID, text and optional delivery (`steer`, `queue`, `interject`). Steer is the default. The native API exposes `POST /api/session/:sessionID/task/:taskID/message` with `{ inputID, text, delivery? }`, and passive receipt reads at `GET /api/session/:sessionID/task/:taskID/message/:inputID`. The model tool derives a stable input ID from its canonical caller/message/tool-call identity; operators must retain their input ID across uncertain network results. The existing permission alias maps `send_subagent_message` to canonical action `task`; its resource is the target Session ID. This preserves existing Task permission policy rather than introducing an independent permission grant.

Receipts distinguish admitted, promoted, cancelled and interrupted. Only unpromoted inputs acquire cancellation/interruption; promoted text is never represented as undone model work. A foreign or replaced service owner does not prove process death, so passive message reads retain durable admission evidence without fabricating a terminal state. Admission/promotion require the live launch and never wake old work. Exact equivalent retries retain the same receipt and consume no quota. Conflicting text, delivery or target is rejected. Removed/reverted canonical input cannot be reconstructed from a private receipt.

Text must be nonblank and at most 32768 UTF-8 bytes. This stage applies native persistence bounds of 32 pending inputs, 1 MiB pending text and 128 total admitted deliveries per launch. These bounds are explicit native adaptations; source-specific granted-sender limits and broader routing are still follow-on work.

## Ownership and transaction boundaries

The private Task-message table contains launch binding, Created proofs, operation, byte count and receipt state. Text remains solely in `session_input`. A launch starts with admission closed; registration opens it once, and final idle/cancellation permanently closes it. Admission uses the existing PromptAdmitted EventV2 transaction for both canonical input and binding. Permission/model/network waits do not hold write transactions. Quota or authority rejection rolls back the input and its event.

The existing owned runner promotes the initial input, then authorized interjects and steers in stable admission order within each class. Queue remains pending until continuation would otherwise stop and promotes one message before reevaluating. The final idle decision and admission close share a short immediate transaction, so a racing send either produces continuation or is rejected without an orphan input. Provider execution continues in the same Task launch with one existing stream call per provider turn. Ordinary Session/Goal/Workflow ordering is unchanged.

Generic pending and promotion selectors exclude launch-bound inputs; the explicit owner promotion callback validates the live launch inside the Prompted commit before publication. Durable PromptWithdrawn plus `withdrawn_seq` preserves unconsumed admission evidence, rejects stale selected promotion transactionally and replays without creating a visible user message. Headless outcomes are not fabricated or reused as generic withdrawal.

Interject may race only existing passive `task_wait` and `process_wait` tool leaves against a launch-owned signal. The signal is a hint: pending durable interject and current launch authority are revalidated before the wait ends. The interrupted tool result carries `interruptedByMessage`; timeout is not fabricated, and target execution is not cancelled. Provider calls, arbitrary tools, permission prompts and foreground Task execution are not interrupted. Current managed-child restrictions generally prevent creating a new background wait target from a Task child, so natural-product wait-target acceptance remains limited by that existing surface. This stage does not relax those restrictions.

## Completed-child tool wake candidate

`send_subagent_message` can now start a new owned background launch of a completed direct child when the sender is an ordinary root Session with live `CurrentChildren` ownership. It preserves the child Session, transcript, selected agent, captured model, Created proofs and historical launch receipts. The operation reuses `SessionTask.launch` and the existing BackgroundJob/Session coordinator; it adds no executor and does not resume the old launch. Existing explicit `task({ task_id, ... })` follow-up remains available.

The canonical input and its message-to-launch binding commit together through PromptAdmitted. Initial admission rechecks the sender's current agent, parent/child Created proofs, active-message configuration and Goal eligibility. Canonical launch permission/model admission still applies, and the wake role intersects historical authority with current child-agent and sender permission envelopes. Ordinary inbox selectors cannot consume this launch-bound input. The new owner promotes the initial message once; queue also starts this new run at its initial idle boundary. The requested delivery remains visible on the receipt. Unpromoted messages retain cancellation/interruption evidence when their launch closes.

An exact retry resolves the canonical input and old receipt before considering the child's latest launch, so retrying a promoted message does not create another launch or provider call. Conflicting reuse fails. A fresh HTTP/operator send to a completed child still returns conflict: it has no live model-tool child capability. HTTP receipt reads and exact retries of the model-admitted input remain supported. Failed/cancelled launches, descendant routing, nested background execution, managed Workflow/reviewer/headless sends and Goal-owned background wakes are not enabled by this slice. Existing generic selectors, task admission and scope finalizers enforce those boundaries.

The pinned source revision `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8` documents inactive delivery as the next turn in `send_subagent_message.rs`; `task/coordinator/wake.rs` rechecks the sender, retains the child identity and creates a new background run. Its wake tests cover all three delivery modes. These files were inspected as reference evidence; upstream tests were not counted as Apexo verification. A fresh isolated Grok 1.0.52 comparison passed all eight existing delivery scenarios with 48 conversation and 42 auxiliary requests, including completed-child same-ID wake with two child turns and one admission.
