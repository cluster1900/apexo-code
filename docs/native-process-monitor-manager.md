# Native Shell and Monitor management in the Tasks UI

The existing Tasks manager presents native child Tasks, Shell processes and Monitors. App, mini terminal and fullscreen terminal use the selected Session transport; explicit native selection on a mixed server must stay on the native endpoints. Compatibility Sessions keep the existing compatibility Task controls.

Each row carries its source as well as its ID. Actions never infer source from an ID prefix or title. Native Task and process lists load independently, are combined by newest start time with a stable source-qualified tie-break, and are capped at 100 displayed rows. A failed source leaves available rows visible, shows a fixed source-specific warning and marks the running total unknown. Recovery clears that warning. The count refers only to the displayed recent list, not lifetime process totals.

Details preserve actual Monitor kind, persistent policy, effective timeout, accepted/suppressed batch counts and overload status. Batches are neither line counts nor provider calls. Persistent Monitors still become interrupted after a server restart; the UI offers no restart/resume action. Actual retained output, truncation and exit code remain readable. Monitor model Stop suppresses delivery until real new user input; Stop process ends the owned command. Passive list/get/wait does not rearm delivery or start model work.

The explicit wait action observes a native process for ten seconds. Timeout leaves it running. Changing selection or closing the manager stops only the observation. Cancellation is the existing bodyless native POST and waits for the owned command's joined settlement. Safe fixed error text distinguishes stale/busy, missing, unavailable and general failures without rendering server causes. Terminal panels retain a stable outer root and expose PageUp/PageDown for the output and metadata area.

No Core service, API, public schema, generated client, process runner or permission behavior changes in this slice. The existing native Monitor CLI/Desktop backend and installed-reference acceptance remain separate evidence; they do not establish renderer correctness.

Private verification so far: App and TUI adapter suites each passed 24 tests / 91 assertions; Final App, TUI and Apexo package typechecks all passed. The final focused footer renderer gate passed 2 tests / 10 assertions, including the same-key refresh/wait regression after its red reproduction. Actual native mini/fullscreen at both 120×40 and 80×24 each passed six checks with 21 setup-provider calls and zero UI-provider calls. Explicit native selection on mixed hosts passed five checks in each 80×24 terminal mode, also 21 setup calls and zero UI calls. Existing actual compatibility mini/fullscreen Tasks fixtures passed unchanged.

The private production browser passed eight checks with real en/zh/zht Monitor restart and overload screenshots, passive timeout/close, joined cancellation, independent list failure/recovery, retained output/exit/truncation and narrow layout. Its 50 provider calls belong to fixture setup and actual Monitor event delivery; UI actions added zero calls. The Simplified Chinese overload and Traditional Chinese restart screenshots were visually inspected. The actual private native window passed the same eight checks with 50 fixture setup/event calls and zero UI calls; its running and Traditional Chinese overload screenshots were visually inspected. All owned build, renderer, PTY and typecheck processes were reaped. Shared integration, rebuilt artifacts and performance verification are root-owned and are not claimed by these private results.
