# Native Plan approval presentation

The existing QuestionDock presents Plan approval. The optional `plan_approval` purpose is presentation-only and is not exposed in model Question prompts. It never authorizes execution. Canonical option labels are retained in selection state and submitted answers even when visible labels are translated. The plan question, path and artifact content remain exact server data.

English source labels and descriptions are preserved. Simplified Chinese uses 计划审批, 批准 and 继续规划; Traditional Chinese uses 計畫核准, 核准 and 繼續規劃. The actual agent identifiers `build` and `Plan` remain visible as existing developer-facing names. Other locales retain the established English fallback for these five new keys. This is corpus/context review, not native-speaker certification.

Terminology review used the maintained [VS Code Simplified Chinese corpus](https://github.com/microsoft/vscode-loc/blob/main/i18n/vscode-language-pack-zh-hans/translations/main.i18n.json) and [Traditional Chinese corpus](https://github.com/microsoft/vscode-loc/blob/main/i18n/vscode-language-pack-zh-hant/translations/main.i18n.json), including approval and plan-review controls; the independent [Firefox Simplified Chinese](https://github.com/mozilla-l10n/firefox-l10n/blob/main/zh-CN/browser/browser/preferences/preferences.ftl) and [Traditional Chinese](https://github.com/mozilla-l10n/firefox-l10n/blob/main/zh-TW/browser/browser/preferences/preferences.ftl) continue/review wording; and GitHub's maintained [Chinese Plan mode documentation](https://docs.github.com/zh/enterprise-cloud%40latest/copilot/how-tos/copilot-in-your-ide/use-copilot-agents/use-plan-mode). Existing Apexo Goal planning terminology is retained. Regional Traditional Chinese planning/approval phrasing remains suitable for native-speaker review.

The first actual production browser run passed 5 checks/4 calls across en/zh/zht, including exact full textContent, keyboard navigation between two canonical choices, no unsupported custom answer, and a translated approval that submitted canonical `Approve` to the actual native endpoint. Screenshots were inspected. They also exposed the separate need to preserve visible newlines and wrap long artifact paths; final visual acceptance follows that scoped repair. Actual native-window and paired production benchmark acceptance remain root-coordinated integration gates.

The final long-document browser pass completed 6 checks/6 calls. Screenshots at the bottom of the 80-line document visibly retain the final marker and wrapped long token. The view now preserves whitespace and limits only the viewport height; it does not truncate stored or displayed text. The generic custom:false contract hides unsupported free text, while ordinary omitted/default custom answers and keyboard navigation remain available. The same final run typed and submitted an ordinary custom answer through the actual native endpoint, preserved its exact text, and observed one provider continuation.

The national dictionary search was attempted but unavailable through the documentation tool, so no unobserved dictionary entry is cited as reviewed. Maintained developer/product corpora support the terminology; this limitation and lack of native-speaker signoff are explicit.

Shared integration: production browser and rebuilt actual Desktop each passed six checks / six calls, including the full scrollable artifact, both Chinese locales, canonical approval and ordinary custom submission. Final screenshots were inspected. The first native harness failure selected a CORS preflight rather than the POST; BUG134 records the causal repair. All 21 shared typecheck tasks passed. The [paired composer measurement](testing/performance/native-media-plan-composer.md) is complete with preserved backend/artifact hashes; it does not establish a causal timing difference.
