# BUG-20261015-186: Mixed-terminal reconnect acceptance never disconnected the stream

- **Status:** Fixture corrected and verified against the packaged backend in both terminal modes.
- **Scope:** `grok-native-terminal-tui.mjs --mixed --desktop --reconnect` and its owned recording proxy. One authoring episode; no product reconnect defect is established.
- **Observed:** The terminal completed its actual Question reply but timed out waiting for a third `/api/event` request. The mixed recording proxy and packaged server had kept their SSE connections healthy throughout the scenario.
- **Expected:** A reconnect test must disconnect its owned event transport before expecting a new subscription, then verify restored state without extra provider work.
- **Reproduction:** Run the command above from `packages/apexo` before the correction. Inspect the retained request log: two SSE subscriptions belong to the fixture observer and terminal, with no induced transport close.
- **Root cause:** The assertion was reused from the pure-native source fixture, whose listener could close on its default idle deadline. The mixed server has a persistent event transport, so that incidental trigger did not apply.
- **Fix:** Track event connections in the owned mixed-server proxy and expose an explicit disconnect action. Invoke it before waiting for the terminal's resubscription. The backend and Session stay alive; the original provider-count and durable-state assertions remain unchanged. Other API traffic and unrelated application connections are unaffected.
- **Verification:** Formatter and syntax checks passed for the actual helper and terminal script. Corrected packaged mixed mini/fullscreen reconnect acceptance each passed five checks / three provider calls and exited zero. Both restored canonical state, admitted the next user prompt and stayed on native routes; reconnect itself caused no extra provider work. Owned PTYs, proxies and backends were reaped. The earlier pure-source passing run is separate evidence.

The first explicit-disconnect attempt still timed out. A private lifetime trace identified why: on pinned Bun, `ClientRequest.close` arrived 10–16 ms after each SSE response opened while the outgoing response still had `writableEnded=false`. The proxy removed both still-live event connections at those callbacks, leaving an empty map at disconnect. The actual response-close events occurred only during teardown about 26 seconds later. Connection bookkeeping now follows the outgoing response's close event and destroys its associated upstream there. This is part of the same fixture implementation episode, not evidence that the terminal failed to retry an actual disconnect. The corrected two-mode results above verify the intended reconnect scenario.
