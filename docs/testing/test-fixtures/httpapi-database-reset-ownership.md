# BUG-20261015-175: HTTP fixture reset removed a database before its owners closed

- **Status:** Reset ordering and the independently isolated process-global Worktree adapter owner are repaired. Shared focused verification and the complete three-mode HTTP gate pass.
- **Scope:** `packages/apexo/test/server/httpapi-exercise` service teardown and isolated database reset. One diagnosis episode; repeated warnings in that run are not independent occurrences.
- **Observed:** A phase-traced, unchanged 98-scenario subset passed its assertions but recorded four `Goal cleanup recovery failed` warnings with SQLite `disk I/O error`. The complete gate had also emitted this warning. This is separate from the unexplained [Session read deadline](../test-stability/httpapi-session-get-timeout.md).
- **Expected:** Close owned HTTP handlers and scenario service scopes before deleting database, WAL and shared-memory files. Test reset must not construct an unrelated process-global application runtime.
- **Reproduction:** From `packages/apexo`, run the Effect HTTP exerciser with `--include /session --start-at session.list --stop-at session.get.missing --trace --progress`, preserving its isolated global directory/database through the supported exercise environment settings. Inspect the owned application log as well as scenario assertions.
- **Root cause:** `withContext` ran its reset finalizer before the enclosing scenario scope closed. Reset called generic fixture helpers that initialize the process-global compatibility `AppRuntime` merely to dispose instances; that runtime retained its own database and periodic Goal cleanup owner. The harness then unlinked database files while those services still referenced them. Its extra 25 ms sleep did not establish ownership settlement.
- **Fix:** Close the cached web handlers before closing the scenario scope, then reset only the harness-owned database files. Remove the generic runtime-disposal/reset helpers from the exercise runtime contract. Preserve authorization-mode behavior and explicit database-preserving scenarios. Do not ignore database-reset errors or use a timed delay as proof of release.
- **Verification:** `bun typecheck` in `packages/apexo` passed. The corrected Effect exercise from `/session/status` through `session.get.missing` passed all four scenarios, exited zero and emitted no Goal cleanup recovery or SQLite I/O warnings. Scenario traces include successful response/assertion and temporary-directory cleanup phases. No production Session, Goal or database code was changed.
- **Limits:** The original 98-scenario run already passed `session.get` without this fix. This correction therefore does not establish the cause or repair of BUG174. The final complete gate and remaining integrated feature checks must be recorded separately.

The private repair passes the caller's Worktree service through the internal adapter context. Built-in configure/create/list/remove operations use that service with the explicit instance/workspace context rather than starting `AppRuntime`. The Workspace node declares the dependency. The Promise bridge passes its cancellation signal to the built-in operation; custom Promise adapters retain their existing method contract. No global runtime disposal is added to per-scenario cleanup.

A child-isolated regression observes the real runtime entrypoint while delegating every invocation unchanged: original code fails because synchronization starts the global owner; repaired code must complete the same actual HTTP route without constructing it.
