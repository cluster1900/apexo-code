# BUG-20261015-356: Native legacy Dream fixture assumed nonexistent LLM reply helpers

- Scope: The new native legacy Dream held-provider regression.
- Observed: The first focused run passed ten tests and failed one before reaching the held provider. Runtime reported `llm.reply is not a function`; package typechecking also rejected `llm.reply` and `reply.text`.
- Expected: Use the actual TestLLMServer public hold API, keeping a real local provider request and explicit release.
- Root cause: The test author assumed a reply-builder shape instead of inspecting the fixture service. This is a fixture API contract error, not a Dream lifecycle failure.
- Fix: Use `llm.hold(text, promise)` with a scoped release finalizer and `llm.wait(1)` readiness.
- Verification: The repaired test reached the model and mode-change boundary. A subsequent assertion incorrectly expected cancellation from a mode disable; SessionMemoryModeNative deliberately fails its race with `changed`, so the existing operation owner records failed. The fixture now asserts that contract and independently verifies no memory publication. The final focused run passed 26 tests / 153 assertions, including bounds, NO_REPLY and selected-Agent replacement. Core and Apexo types passed.
- Occurrences: One new fixture API authoring episode; the later status assertion is not an additional occurrence.

The separate before-feature CLI probe initially expected HTTP 409 for unsupported native Dream. It observed 403; the corrected probe verified the exact unsupported message and zero provider calls. The established unsupported-operation mapping is documented in [BUG-20261015-242](../runtime/memory-operation-unsupported-status.md). This related authoring note is not counted as a recurrence of the LLM helper error, and no product fix is claimed for either fixture assumption.


The crash probe first observed only SQLite `all/get/run`, while native Drizzle uses `values`; its prepared-checkpoint poll timed out. Observing `values` after its actual write made the prepared crash run pass. A separate file observer based on mutating `fs/promises.rename` did not intercept Bun's named binding and timed out. The replacement narrowly scoped Bun loader observer parks after the actual atomic rename, and both MEMORY-before-state and state-before-settlement process-death runs passed. These are observer setup corrections in the same new fixture authoring work, not independent occurrences of the LLM helper root cause. No production result is mocked or weakened.

The first native-window command attempted an unpinned `bunx agent-browser` resolution and failed before controlling the app because that transient package resolution lacked its platform executable. The fixture now accepts an explicit existing browser executable. The next attempt navigated with a synthetic anchor before the Desktop router was ready, producing a renderer file-not-found page. Waiting for the restored Session controls after initialization/reload fixes that setup race. Native-window acceptance then passed four checks with one provider call. The screenshot checkpoint was also moved after the actual rendered result status and enabled retry control, since an existing row alone can still display queued state. These are separately identified fixture setup issues, not extra occurrences of the LLM API mistake or product Agent defects.

## Batch fixture authoring notes

The batch deferral test initially called nonexistent `store.context`; the actual store exposes `contextNotes`, and the corrected assertion checks the exact remembered source file's presence after each durable attempt. The installed batch fixture renamed its parsed `input` diagnostic to `batchCall` but retained a stale `input` field reference, causing local provider HTTP 500 replies and a main-turn timeout. Recording the actual current user content fixed that fixture, after which the isolated installed comparison completed the list/action/create exchange and repeat-no-provider checks. These separately identified fixture corrections are not product failures or additional occurrences of the legacy LLM-helper error.

Final batch typechecks also exposed an owned-store revision callback whose declared channel omitted the real capture/storage error conversion, a sort attempted directly on a readonly path array, and a plain string expectation against a branded path. The implementation now preserves the owned revision's actual error channel, sorts a copied array, and compares the explicit path string. These diagnostics were corrected without casts or weakening production schemas; Core and Apexo typechecks passed before the later result-display additions, which require their own final checks.
