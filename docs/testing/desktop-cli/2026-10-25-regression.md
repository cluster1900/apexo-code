## Goal evidence

A minimal request through the real native Antigravity adapter reproduced HTTP 400 when the history ended in an assistant turn. The upstream diagnostic was `Requests ending with a model turn are not supported.` Adding the corrective user turn succeeded with the requested response marker. This identifies a request-shape problem rather than an account failure.

A separate real Desktop Goal deliberately returned `WRONG_ON_PURPOSE` on its first worker attempt. Independent review requested correction, and the next worker response was exactly `GOAL_CORRECTED_OK`, with no HTTP 400. The server transcript contains two distinct successful assistant turns and no extra durable corrective user message. Independent evaluation confirmed the transition. During the additional adversarial verification, a verifier requested an out-of-scope recursive search of user/system directories; it was denied and the Goal paused with review failure at 384730 tokens. That final stage is not counted as completed. The separate 485621-token lifecycle run below supplies full 3/3 completion evidence.

The full deterministic Goal integration test executes a rejected worker result followed by another worker turn, independent evaluation and completion. It verifies the second worker request ends in a user turn and that the durable transcript still contains only the original user message.

A real Desktop 200000-token Goal produced the correct marker, passed evaluation and reached one independent verifier, then correctly stopped because the remaining 3354 tokens could not fit the estimated 20120-token context. That budget-limited run is not counted as completed. A subsequent Goal with a 600000-token budget reaches **Verified complete**, with all 3/3 independent verifier reports confirming requirements and 485621 reported tokens. Its final response is exactly `GOAL_RECOVERY_OK`.

## Production session benchmark

Five samples per production bundle use the same retained fixture transcript and viewport. The pre-change medians were 187.61 ms to open the session and 169.49 ms to open Context. An intermediate fixed bundle measured 187.02/160.14 ms. The final bundle was also measured during full-suite load (383.81/344.34 ms); that unmatched-load result is retained but is not sufficient to attribute a performance regression. With both bundles measured under the same remaining HttpApi workload, medians were 354.89/275.17 ms before and 334.28/301.34 ms after (session −5.8%, Context +9.5%). After all test workers and generators finished, the final idle comparison measured 213.14/185.53 ms before and 205.44/191.67 ms after (session −3.6%, Context +3.3%, a 6.14 ms Context delta). Five-sample results are descriptive rather than a formal statistical performance guarantee.

## Evidence limits and intermediate failures

- The first Context patch covered legacy helpers but missed the active server-session cache. Its real Desktop run still showed 7 messages/2 users versus 6/1 on the server. The active path was then fixed, directly tested and rerun successfully in a fresh window.
- HTTP/queue integration fixtures supplement live acceptance; they are not substituted for real model execution.
- The original 43-case matrix contains broader settings, navigation and packaging coverage. This follow-up reruns the affected issue paths and core coding flows; it does not label every original case as newly executed.
- Root-cause and fix records: [runtime defects](../runtime/antigravity-acceptance.md), [UI/TUI defects](../ui/desktop-cli-acceptance.md). No new recurring constraint is promoted from this one fix cycle.
