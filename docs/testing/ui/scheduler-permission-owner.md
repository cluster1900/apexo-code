# BUG-20261015-244: Permission presentation disposed the Scheduler action owner

- Status: Corrected in the private Scheduler UI; browser and rebuilt native-window approval/denial and owner cancellation verified.
- Scope: Shared App Task/Process/Scheduler manager ownership across both composer variants; one reproduced integration episode.
- Observed: Resume raised an actual task permission request. The blocked composer branch removed the component owning `createSessionTasks`, aborted its request signal and discarded pending/error state. Returning from Deny showed no action feedback. An isolated diagnostic logged cleanup with the exact pending Schedule key.
- Expected: Showing permission UI must not destroy the Session-owned manager action. Explicit rejection remains visible and paused; approval can complete the existing action without another model turn. Session ownership changes still clean up requests.
- Root cause: the controller was created inside either composer, both of which may unmount while a permission/question dock occupies the input region.
- Fix: create one controller in the Session page and pass it through optional typed props to both composer variants. Standalone usages retain their existing local fallback. Task, Process and Schedule actions share this controller. The existing Session-ID/SDK effect retains its abort and timer cleanup.
- Verification: `bun script/grok-native-scheduler-ui.mjs browser --permission` exercises real ask, Deny and Allow once. Browser and rebuilt native-window runs each pass two checks. Five setup provider calls remain five throughout management. App types pass; the focused App transport/localization suite passes 31 tests / 367 assertions, including a real held HTTP owner-abort check in a native child.
- Boundaries: hiding a still-owned Session tab is not disposal. The actual tab-close fixture preserves paused intent and no provider work; client and backend cancellation evidence are kept separate. The native-window tab-close HAR records `net::ERR_ABORTED` for the pending Resume request. The private backend's empty 500 response to explicit denial is the distinct BUG-20261015-250 mapping defect, separately fixed and verified in the shared backend; response ordering alone does not prove cancellation. No backend fix or joined server cancellation is claimed here. Diagnostic console logging is excluded from product code.
