# BUG-20261014-180: Plugins management assumed compatibility routes and enabled meant active

- Scope: App/Desktop Plugins management and shared terminal Plugins actions.
- Observed: all management requests selected the compatibility `client.plugins` group even for native-only servers. The catalog showed installation enablement but exposed no native project activation snapshot or failed-activation state.
- Expected: native servers use `client.v2.plugins`; mixed servers retain compatibility semantics. Catalog installation/enablement and project activation are displayed independently. A failed apply preserves the prior active snapshot and presents the failure; busy errors remain visible even though passive runtime status does not persist them.
- Reproduction: open Plugins while connected to a native-only server, then list/install/apply a plugin. For activation semantics, enable a supported bundle, inspect before applying, apply it, then attempt to apply an unsupported MCP bundle.
- Root cause: Plugins management was implemented before the native management group and activation lifecycle existed. Compatibility-only routing and catalog-only state could not represent the native boundary.
- Fix: App selects its existing detected protocol for list/detail/manage and uses Location-scoped native runtime/reload operations. It shows the separate active snapshot, typed activation errors, and an explicit Apply action. Terminal adapters lazily prefer legacy health on mixed servers and fall back to native health only when legacy health is missing; the shared panel renders separate enabled and active states. Requests are aborted on close, and App runtime state resets when server/project changes.
- Verification: App and TUI package typechecks passed after generated SDK readiness. The real compact and expanded native-actions PTY harness each passed six checks: passive native list/runtime, enabled versus active, explicit activation, unsupported failure preserving the prior snapshot, successful recovery clearing the previous failure, and no model work. The captured terminal screen showed the failure and retained active plugin together. These harnesses exercise the shared production panel and native action adapter; they do not establish complete native-only terminal bootstrap. The actual compatibility mini and fullscreen app commands `bun script/grok-plugins-tui.mjs` and `bun script/grok-plugins-tui.mjs --fullscreen` each passed eight checks, including slash entry, list, download, trust/install, disable, details, uninstall, and no model call. All four PTY runs were reaped. `bun script/grok-native-plugins-ui.mjs desktop --locales` and `bun script/grok-native-plugins-ui.mjs native --locales` each passed eight checks against the actual native-only source server, using the production App build and real macOS Electron window respectively. Both verified download/detail, enabled versus active, explicit activation, unsupported MCP preserving the old snapshot, zero model work, Simplified/Traditional Chinese failure panels, and successful recovery clearing the failure. Screenshots were inspected: controls and diagnostics were readable, and enabled and active states were separate. Both fixtures were reaped. `bun script/grok-plugins-ui.mjs desktop` also passed 24 checks against the compatibility Desktop backend, covering management, source changes, nine localized storefronts including Arabic RTL, and narrow-screen overflow. That fixture was reaped. No composer entry points were changed.

## Localization review

New App copy is localized in Simplified and Traditional Chinese; other locales retain the shared English fallback. Existing English strings are unchanged. The terminal panel retains its established English-only interface.

Terminology and grammar were checked against Microsoft's maintained [Simplified Chinese VS Code corpus](https://github.com/microsoft/vscode-loc/blob/main/i18n/vscode-language-pack-zh-hans/translations/main.i18n.json) and [Traditional Chinese corpus](https://github.com/microsoft/vscode-loc/blob/main/i18n/vscode-language-pack-zh-hant/translations/main.i18n.json), plus Mozilla's [Simplified Chinese add-ons corpus](https://github.com/mozilla-l10n/firefox-l10n/blob/main/zh-CN/toolkit/toolkit/about/aboutAddons.ftl) and [Traditional Chinese corpus](https://github.com/mozilla-l10n/firefox-l10n/blob/main/zh-TW/toolkit/toolkit/about/aboutAddons.ftl). The [Taiwan Ministry of Education definition of 設定](https://dict.revised.moe.edu.tw/dictView.jsp?ID=129562&la=1&powerMode=0) supplied a language-authority check. Existing Apexo terms 插件/外掛程式, 项目/專案, 加载/載入, 配置/設定 are preserved. 生效 distinguishes current project activation from the catalog's existing 已启用/已啟用 label; this distinction and the complete activation hint should receive native-speaker review. MCP/LSP remain protocol capability identifiers, and backend diagnostic messages remain server-provided data.
