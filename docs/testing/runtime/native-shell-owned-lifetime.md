# BUG-20261015-361: Native owned Shell lifetime inherits the short foreground default

- **Scope:** Native Bash timeout resolution into existing immutable Session process requests.
- **Observed:** Omitted owned/background timeout was always recorded as 120,000 ms. Zero and positive values above 600,000 ms failed the tool input schema. Foreground wait settings therefore promoted the same process but could not express the reference's long-lived background behavior.
- **Expected:** Eligible owned execution with omitted or zero timeout uses a ten-hour safety cap. Positive owned deadlines may extend to that cap. Foreground defaults/restrictions, native command authority, managed/Goal/headless restrictions, exact receipt retry, cancellation and Stop remain authoritative.
- **Reproduction:** From `packages/apexo`, run `bun test --timeout 30000 test/v2/shell-lifetime.test.ts` against the preceding implementation. Five foreground/short-deadline controls pass and three owned lifetime cases fail: omitted records the wrong deadline; zero and 700,000 ms do not launch.
- **Root cause:** The native Bash input and request resolver reused foreground validation/defaults for owned execution. The underlying process executor already supports an explicit recorded duration, so no second executor or timer owner is needed.
- **Fix:** Allow a nonnegative input up to 36,000,000 ms, reject zero or values above 600,000 ms before spawning when the call is not eligible for owned execution, and resolve owned omitted/zero to the explicit ten-hour cap. Keep positive owned deadlines unchanged. The immutable process request holds the resolved duration and the existing executor enforces it. Monitor zero/persistent behavior is untouched.
- **Verification:** The expanded native suite passes 40 tests / 386 assertions. Core and Apexo typechecks pass. The final fixture guard rerun passes ten tests / 34 assertions. Source CLI exercises omitted, zero, 700,000 ms and a real 40 ms deadline; long-lived cases survive the unrelated one-millisecond host wait ceiling and are explicitly cancelled with joined PIDs. Isolated installed 1.0.52 comparison passes three cases / six conversation and ten auxiliary requests. Ten-hour resolution is checked in actual durable requests; the test does not claim a ten-hour wall-clock run. Rebuilt Desktop remains an integration gate.
- **Occurrences:** One confirmed native capability gap; no new recurring constraint.

The pinned source resolves background omitted/zero to `Duration::MAX` in `bash/mod.rs`, while `computer/local/terminal.rs` independently enforces `BACKGROUND_MAX_RUNTIME` of 36,000 seconds. Apexo records that safety cap explicitly. This is capped execution, not unlimited lifetime.

The current reference contract folds `block_until_ms: 0` into background execution and discards the legacy `timeout`, including a positive value. The isolated probe confirms omitted, zero and positive 40 ms all remain alive through its 200 ms observation with explicit zero block. Apexo deliberately retains its documented separate millisecond process deadline: a positive timeout still kills at that deadline. Its ordinary foreground path retains the two-minute default and ten-minute maximum; it does not adopt the reference's timeout-to-wait alias.

The first expanded native run passed 37 tests and failed one new fixture assertion. A 40 ms deadline includes shell startup and may terminate execution before the shell writes its PID file. The fixture had treated that file as mandatory after timeout. The corrected assertion requires terminal deadline settlement and checks reaping whenever a PID was published; long-lived cases still require a published live PID and joined cancellation. The CLI uses the same distinction. No timeout was increased and no product change was made for this fixture assumption.

The initial Apexo typecheck also identified an optional expected-deadline value in the newly parameterized fixture. The fixture now explicitly rejects missing expectations for owned cases before the typed assertion; no cast or production type weakening is used. This is a supporting fixture correction, not an additional product occurrence.
