# BUG-20261014-154: Compatibility services retained a closed Location map

- **Scope:** Compatibility AppLayer and HttpApi service graphs sharing a memo map.
- **Observed:** The first project prompt completed, but a later project prompt returned an aborted assistant with no provider request. Async prompt and command requests likewise stopped before provider execution. The interruption originated in `SystemPrompt.environment` while acquiring native Location services.
- **Expected:** Releasing one project's setup scope must not invalidate services still used by the shared server for another project.
- **Reproduction:** Run `bun script/httpapi-exercise.ts --mode effect --include session.prompt` from `packages/apexo`. The harness shares the production HttpApi memo map and closes each project's AppLayer scope before the next scenario. Before the fix, the first ordinary prompt succeeded and the next async prompt timed out without reaching the local test provider.
- **Root cause:** Adding the native Session execution dependency made default compatibility graph compilation discover an unbound Location map. Each AppNodeBuilder call constructed a different map layer, while service implementation layers were shared through memoization. A retained SystemPrompt instance could therefore capture the first graph's map after its owning scope closed.
- **Fix:** Default AppNodeBuilderV1 graphs use one stable Location map layer identity, including the compatibility bootstrap replacement. Graphs with explicit replacements retain their prior compilation behavior. This does not claim arbitrary custom replacement graphs can safely share all memoized implementations.
- **Regression:** `test/server/httpapi-location-lifetime.test.ts` runs real sequential project requests through the shared HttpApi setup and requires both provider-backed requests to succeed after the first scope closes. A fresh server per request would hide the defect.
- **Verification:** The focused route selection changed from 2 passing / 1 failing scenarios to 3 passing / 0 failing scenarios. The dedicated HTTP lifetime regression passed (1 test, 2 assertions). The explicit map override plus Runner/snapshot/adapter batch passed (35 tests, 105 assertions). All six compatibility provider HTTP scenarios passed. Final `bun typecheck` from `packages/apexo` exited 0. The complete HTTP gate subsequently passed all 271 scenarios in each of coverage, authorization and Effect-handler modes, with zero failures, skips, missing routes or extras.

## Second integration occurrence: live maps diverged after MCP reload

The native MCP CLI fixture exposed a separate symptom of the same service-map ownership error. After a process restart, disabling the installed MCP bundle and reloading returned an empty native MCP status, but the seventh fresh provider request still advertised its tool. Both maps remained live; this was registry divergence rather than the original closed-owner interruption.

The mixed server graph supplied its explicit native map to handlers while the compatibility application graph could construct the process-global Session execution service using its default map. Shared memoized implementations then retained that different owner. The fix uses the stable default AppNodeBuilderV1 map in the mixed server and injects that map into both graphs without changing process-global Session execution semantics. An intermediate fix shared only a new map inside the server; the old sequential-project regression still failed because the shared AppLayer could retain the other map. Sharing the default map across all three entrypoints resolved both symptoms.

`bun script/grok-mcp-native.mjs cli` reproduced the final provider-tool assertion failure before the fix and passed all eight checks with seven real provider requests afterward. The regression requires a new provider request after disable/reload and inspects its advertised tools, so a passive status response cannot hide the divergence. The sequential-project lifetime and explicit replacement tests also passed (2 tests, 3 assertions), and final Core/Apexo type checks passed. Full mixed-route verification is tracked separately after the focused source freeze.

These are two independent integration occurrences sharing incorrect Location-map ownership through memoized service composition. They do not yet qualify for a recurring constraint.
