# BUG-20261015-306: Interrupted metadata readiness released its lease before recovery persistence

- Scope: new MemoryMaintenance.writeEffect readiness during interrupted change recovery.
- Observed: review identified interruptible Promise ownership; a deterministic isolated-child negative control then reproduced it. While the first real recovery rename was held, interruption completed and a competing writer entered a second recovery rename under the released lease.
- Expected: bounded readiness persistence settles before interruption releases the maintenance lease. Waiting for the lease must also be interruptible; a subsequent audit found a separate canonical Flock.effect defect, now corrected with an actual held-wait regression in [BUG-20261015-326](flock-effect-acquisition-cancellation.md).
- Reproduction: write a real pending change marker, start writeEffect, hold only its filesystem rename in a child-local wrapper, interrupt, and start a competing real writer. Observe interruption completion and the count of entered renames before releasing the gate.
- Root cause: interruptible Effect.tryPromise does not cancel or join underlying filesystem promises. The scoped Flock finalizer could run while ready continued saving recovery state.
- Fix: mark only the bounded ready Promise uninterruptible. Lock acquisition and the supplied action retain their existing interruption semantics; model/network work stays outside this bounded region.
- Verification: unamended negative control failed with interruption=false (already finished), contender=true (still pending), renames=2. Amended helper passed with interruption=true, contender=true, renames=1; after release both fibers joined and the real marker was pending=false. The actual metadata action never ran after cancellation. The isolated child owns its module wrapper; no shared globals or production test seam changed. Package typecheck passed. This is one reproduced occurrence, not a recurring constraint.
