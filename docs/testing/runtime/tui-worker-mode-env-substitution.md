# BUG-20261015-210: Direct worker environment reads can select the parent mode

- Status: Integrated; shared real Worker tests and all 21 workspace typechecks passed. Compiled native/compatibility selection passed; complete unit regression is running.
- Scope: TUI worker entry selection under pinned Bun 1.3.14, compatibility and native fullscreen callers.
- Occurrences: One independently reproduced runtime boundary.
- Observed: A real compatibility worker received environment flag `0` but a direct `process.env.APEXO_NATIVE_TUI_HOST` selector chose native when the parent flag was `1`. Reversing the flags produced the opposite wrong selection. Enumerating the worker environment showed the correct overridden flag in both cases. Ordinary inherited and empty values arrived correctly; the parent flag remained unchanged.
- Expected: The worker entry must select its implementation from its own runtime environment, before importing either implementation.
- Root cause: Pinned Bun substituted the statically recognized direct environment property from the parent when loading worker code. The Worker constructor's environment override itself was effective. The production worker entry used the same direct-property pattern. This is distinct from [BUG-20261015-207](../test-fixtures/tui-worker-env-source-assertion.md), whose original assertion never constructed a worker.
- Fix: Both callers use a lightweight `createTuiWorker` factory preserving the inherited environment and their explicit `0`/`1` overrides. The entry calls `tuiWorkerMode`, which enumerates actual runtime environment entries before selecting the existing lazy native or compatibility import. There is no parent environment mutation, provider bridge, or eager implementation import.

## Reproduction and verification

From `packages/apexo`, run `bun test --timeout 30000 test/cli/tui/thread.test.ts --test-name-pattern 'forwards the CLI environment'` with pinned Bun 1.3.14. The fixtures launch isolated subprocesses with the opposite parent flag and use the actual shared factory and selector in a real worker. They report runtime enumeration independently of the selector, verify inherited and empty values, and verify the unchanged parent flag. Worker termination and subprocess cleanup are bounded.

With only the selector reverted to the original direct-property expression, the two behavior tests fail (0 passed / 2 failed / 6 assertions): runtime flags are correct while selected modes are reversed. Restoring runtime enumeration makes the full file pass: 11 tests / 23 assertions, including both worker modes and existing CLI argument cases. The existing package test budget is 30 seconds; no scenario deadline was increased.

The shared branch subsequently passed the same 11 tests / 23 assertions and all 21 workspace typechecks (20 unchanged cache hits). This proves source-loaded Worker behavior on the pinned runtime. It does not claim a general fix for every Bun environment substitution site, other Bun versions, compiled CLI selection, or packaged Desktop acceptance. The refreshed standalone macOS arm64 binary also passed actual fullscreen Question interaction with an intentionally opposite inherited worker flag: native five checks / three provider calls, compatibility four checks / four total calls (three Session calls and one ancillary). Both commands used `grok-native-local-terminal.mjs --fullscreen --opposite-worker-mode`, adding `--compatibility` for the compatibility case and selecting the compiled binary through `APEXO_TEST_CLI_BIN`. The build and version smoke test exited zero; all acceptance children were reaped. The complete unit rerun remains in progress.
