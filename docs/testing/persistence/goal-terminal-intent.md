# BUG-20261014-026: Terminal Goal persistence preceded cleanup intent

- Status: Fixed; targeted unit and CLI process verification passed. One identified root cause; no recurring constraint.
- Scope: Core Goal state, compatibility execution, report allocation and durable cleanup.
- Observed: The Goal transaction could commit `complete` or `budget_limited` before the executor's later cleanup call persisted its report manifest. Killing the process between those operations left scratch without a retry job. Expected: committing a terminal Goal also commits cleanup ownership, while live execution remains protected.
- Reproduction: Allocate an old scoped report, backfill it before execution, reserve another report before allocation, exhaust the budget, publish the committed-state readiness signal, and SIGKILL before the executor's cleanup call. Reopen the same database and drain cleanup.
- Root cause: The cleanup enqueue was an independent operation after terminal-state persistence; only post-enqueue crashes were recoverable.
- Fix: Store reserved report IDs in internal Goal state before filesystem allocation. Backfill existing, reliably scoped reports before the compatibility executor begins or resumes. Commit the fixed manifest and terminal state in one SQLite transaction. The manifest includes a process token/PID teardown barrier: another live process cannot release it, PID reuse or permission errors conservatively block cleanup, and a confirmed-dead process permits recovery. The owning process releases the barrier only after execution scope teardown. Retry never discovers a replacement lifetime's IDs.
- Verification: `bun test test/session/goal-cleanup.test.ts test/session/goal.test.ts test/session/goal-files.test.ts` passed 68 tests before retention coverage was added. `bun script/grok-goal-storage.mjs cli` passed 9 checks, including actual SIGKILL immediately after terminal commit, old-report backfill, reserved incomplete reports, live-process protection and retained plan bytes.
- Implementation regression: The first combined run passed 66 tests and failed 2 queue-count expectations. The new atomic job was duplicated by the old post-teardown enqueue; the finalizer now releases the existing lifetime's intent instead of adding a duplicate. The reused-ID fixture now explicitly releases the new lifetime's terminal barrier before expecting an empty queue. The subsequent run passed all 68 tests.
- Final verification: The full four-file Goal/report suite passed 75 tests and 500 assertions. CLI and Desktop storage each passed 11 checks; CLI lifecycle cleanup passed 7 checks on final frozen source. Production Desktop passed all 7 checks again against the refreshed backend containing the final cross-job barrier correction. The Desktop fixture liveness correction is recorded in [BUG-20261014-029](../test-fixtures/goal-terminal-park-node.md).
- Limits: This does not add clustered execution ownership. The PID guard assumes a shared local host/process namespace. Goals already terminal before this implementation, with no durable manifest, remain available for explicit cleanup or Session deletion; they are not inferred to be global orphans.

## Cross-job teardown protection

A final code audit found that a separately queued Goal-clear or Session-delete manifest had no owner field and could bypass a live terminal manifest. The drainer now checks all terminal/retention barriers for the same Session and Goal before processing any manifest. The executor releases its own persisted barrier even if the Goal or Session row has already disappeared. Unit coverage exercises both deletion paths, preserves scratch while teardown remains live, and then removes reports after explicit teardown release. The process fixture additionally queues both deletions from another process, proves the original child is still alive immediately before SIGKILL, and recovers after that signal.

During this patch, a parent combined run reported 237 passes, 1 skip and 1 failure at an intermediate replacement-test assertion expecting the old plan to remain while the new lifetime's terminal barrier was held. The test and cleanup module were edited during that already-running suite. Cached-module/test-version mismatch is plausible, but the original process's precise loaded source versions were not captured, so provenance remains unconfirmed. The stronger assertion was retained. A fresh run after production and test files were frozen passed all 8 cleanup tests and 53 assertions; this is evidence for the frozen implementation, not proof of the overlapping run's root cause.
