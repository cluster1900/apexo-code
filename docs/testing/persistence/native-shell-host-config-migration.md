# BUG-20261015-352: Native configuration drops Shell host settings

- **Scope:** V1-to-native configuration migration and native Bash host configuration.
- **Observed:** A valid V1 configuration containing `toolset.bash.default_block_until_ms`, `max_block_until_ms` and `max_timeout_secs` decodes successfully, but `ConfigMigrateV1.migrate` drops the whole `toolset` object. Native `Config.Info` also lacks the field, and the native Bash leaf resolves only `shell` from configuration.
- **Expected:** Supported Shell host options remain available after native configuration migration and govern the native Shell contract. Existing compatibility-only acceptance must not be presented as proof of native consumption.
- **Reproduction:** With pinned Bun 1.3.14 from `packages/core`, decode `{ snapshot: false, toolset: { bash: { default_block_until_ms: 0, max_block_until_ms: 50, max_timeout_secs: 0.1 } } }` through `ConfigV1.Info`, call `ConfigMigrateV1.migrate`, and assert that the migrated `toolset` equals the decoded one. The assertion fails: the decoded object is present and the migrated value is `undefined`.
- **Root cause:** The previously added compatibility configuration schema and resolver were not carried into native configuration or its Bash executor. Forwarding the field alone would not repair execution semantics.
- **Fix:** Native `Config.Info` retains the existing `ConfigToolset.Info` schema, and V1 migration forwards the decoded object. Native Bash applies the configured omitted wait and both wait ceilings, records the resolved wait in the existing immutable process request, and promotes through `SessionProcessExecution` without restarting or killing the command. Implicit defaults retain ordinary foreground execution in contexts forbidden from background ownership; explicit background requests keep the existing restrictions. The executor rechecks authority at actual admission. Native process lifetime remains separate. Additional command-prefix, output-limit and long-lived background parity remains separately scoped feature work.
- **Verification:** The previous loader failed both the migration assertion and a real native omitted-wait control: the held foreground command prevented the second provider turn for five seconds. After the fix, the expanded focused batch passed 21 tests / 293 assertions; Core and Apexo typechecking passed; source CLI passed six real process cases. The isolated installed 1.0.52 comparison passed three scenarios with six conversation and ten auxiliary requests, retaining live command PIDs beyond each wait before explicit release. Canonical `bun run script/schemas.ts` completed with every tracked schema output unchanged because its compatibility schema already contains these fields; native JSON-schema emission is also tested. Rebuilt Desktop acceptance remains pending integration.
- **Occurrences:** One independently reproduced native configuration omission.

The installed headless reference initially exposed a fixture assumption: `block_until_ms` need not carry a JSON Schema `maximum` when only `max_block_until_ms` is configured in installed 1.0.52. The comparator now records the actual schema and only asserts the explicit seconds-cap maximum it advertises. This reference difference does not weaken native runtime cap assertions.

A separate comparison-fixture readiness correction was required for zero wait: the installed runtime could send its next provider request before the spawned shell wrote its PID file. The original comparator read that file immediately and failed with `ENOENT`, then reached its existing overall timeout. The comparator now waits up to five seconds for the owned PID file before checking liveness. The corrected zero-wait case returned after 16 ms, retained the same live command through the 200 ms observation, and exited successfully after release. This is a supporting fixture correction, not another occurrence of the configuration omission.
